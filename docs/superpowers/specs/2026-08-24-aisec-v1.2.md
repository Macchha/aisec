# aisec V1.2 — closing the documented gaps

**Date:** 2026-08-24
**Status:** Draft (pending review)
**Predecessors:** `2026-07-28-aisec-design.md` (V1), and the V1.1 work that shipped SARIF, the CI gate and the standalone CLI.

## Problem

V1.1 shipped a scanner whose honesty is its main product claim: every check that could not run is named in `skipped[]`, on every run, including clean ones. That claim is now load-bearing, and five defects sit directly underneath it.

Four are documented in the README's own limitations section, which means every user reads them and none of them are fixed. The fifth is not documented anywhere, and is the same "we could not check reads as clean" bug the project has now hit eleven times — this time expressed in the severity scale rather than in a boolean.

None of these need new rules. They need existing rules to actually reach the things they claim to cover.

## Scope

Five items, ordered by dependency rather than by value:

1. **CRITICAL severity** — confirmed malware currently renders identically to a ReDoS.
2. **Registry response cache** — unblocks the 25-lookup cap that manufactures skips.
3. **devDependencies and peerDependencies** — install scripts run for them; nothing checks them.
4. **Config discovery breadth** — four filenames, one directory level, no Cursor, no Windsurf, no monorepo.
5. **`aisec explain <RULE>`** — the reference docs exist and the CLI cannot print them.

Explicitly **not** in this spec:

- **Runtime probe (`aisec probe`) and manifest pinning (`aisec pin` / `verify`).** These are the V2 headline and the only path to MCP004, sampling, roots and elicitation. They also require executing untrusted code, which contradicts `SKILL.md`'s standing instruction not to execute anything in a scanned project. That tension is a design decision, not an implementation detail, and it gets its own brainstorm before any spec.
- **tree-sitter IR.** Unchanged from V1.1: it decides whether the model stays the parser or becomes a second opinion, which reshapes MCP010–MCP015.
- **CycloneDX SBOM export, a published GitHub Action, baseline expiry, known-server list generation.** Real, ranked, and deferred to keep this spec shippable.

## 1. CRITICAL severity

### The defect

`plugin/scripts/lib/findings.mjs:1` declares `SEVERITIES = ['HIGH', 'MED', 'LOW', 'WARN']`. `plugin/scripts/scan-lockfile.mjs:40` maps `VULN_SEV = { CRITICAL: 'HIGH', ... }`.

OSV `MAL-` records denote **confirmed malicious packages**. `rules-sca.md` says they are floored at CRITICAL internally — and then the report scale flattens that back to HIGH. The README admits the consequence: *"the `MAL-` id in the message is the only signal."*

So a tree containing a package that is known malware sorts, colours, gates and renders exactly like a tree containing a regex that backtracks. The most urgent finding aisec can produce is not distinguishable from its most routine one. That is the project's own invariant — two different states must not share a representation — violated in the one place where the cost is highest.

### The change

Add `CRITICAL` as the top severity. It is a real level, not an alias.

| File | Change |
| --- | --- |
| `lib/findings.mjs` | `SEVERITIES = ['CRITICAL', 'HIGH', 'MED', 'LOW', 'WARN']`; `SEV_RANK` shifts, `CRITICAL: 0` |
| `scan-lockfile.mjs` | `VULN_SEV.CRITICAL = 'CRITICAL'`; the `MAL-` floor emits CRITICAL rather than being clamped |
| `gate.mjs` | `THRESHOLDS = ['critical', 'high', 'med', 'low', 'none']`; `critical: new Set(['CRITICAL'])`, and every other threshold's set gains `'CRITICAL'` |
| `to-sarif.mjs` | `LEVEL.CRITICAL = 'error'`; `SECURITY_SEVERITY.CRITICAL = '9.5'` |
| `bin/aisec.mjs` | usage text for the new `--fail-on` value |
| `README.md`, `rules-sca.md` | delete the paragraph admitting the flattening; describe the level |

### Compatibility

`--fail-on high` currently means "block on HIGH". After this change it must block on CRITICAL **and** HIGH. Writing the threshold sets so that every level includes all levels above it is the whole safety property here: a user who upgrades must not silently stop blocking on the worst thing aisec can find. Assert it in a test that walks the threshold table rather than checking each set literally.

Existing baselines need a deliberate decision. `lib/fingerprint.mjs` hashes `id + file + line + message` — **severity is not part of the identity**, and `gate.mjs:78` marks an entry stale only when its fingerprint matches nothing. So a baselined `MAL-` finding keeps matching after this change and goes on suppressing what is now a CRITICAL, with no stale warning.

That is the upgrade hazard, and it must not be fixed by putting severity into the fingerprint — a finding whose severity was re-rated is the same finding, and rebuilding identity would invalidate every baseline in the wild. Instead: `gate.mjs` compares each matched entry's recorded `severity` against the live finding's, and reports a mismatch as a **severity drift** warning alongside the stale list. Suppression still applies — silently escalating past a user's accepted finding is its own failure — but the report says the accepted thing got worse.

### Done when

- A fixture advisory with a `MAL-` id produces a finding at CRITICAL, sorted above every HIGH.
- `--fail-on high` exits 1 on a CRITICAL-only report. (Regression test: this is the upgrade trap.)
- SARIF carries `security-severity: 9.5` and GitHub ranks it above the HIGHs.
- A table-driven test asserts threshold monotonicity for all five values.

## 2. Registry response cache

### The defect

`lib/registry.mjs` performs a bare `fetch` per package per run. Nothing is cached. `scan-lockfile.mjs:11` therefore sets `MAX_DIRECT_LOOKUPS = 25` and pushes the remainder into `skipped[]`.

The cap is a reasonable response to an uncached client, but the effect is that aisec manufactures its own skips. A project with 40 direct dependencies gets 15 packages reported as unchecked on every single run, forever, for no reason other than that the previous run threw its answers away.

### The change

An on-disk cache under `$XDG_CACHE_HOME/aisec` (falling back to `~/.cache/aisec`), one JSON file per `ecosystem/name`, holding the normalised metadata object plus a `fetchedAt`. TTL 24h, overridable with `--cache-ttl <hours>`; `--no-cache` bypasses both read and write.

Raise `MAX_DIRECT_LOOKUPS` to 200. The cap stays — an unbounded lookup count against an untrusted manifest is its own problem — but at 200 it stops being the binding constraint for real projects.

### The trap, stated explicitly

`registry.mjs:24-31` documents that `hasInstallScripts` and `weeklyDownloads` are tri-state: `null` means nobody looked. **The cache must preserve that distinction across the serialisation boundary**, and it must never cache a `lookupError: true` result as though it were an answer.

Concretely:

- A successful lookup caches the full object, `null` fields included.
- A 404 (`found: false`, `lookupError: false`) **is** a real answer and is cacheable — the registry told us the package does not exist.
- A timeout, a 5xx, or an abort (`lookupError: true`) is **never written to the cache**. The next run must ask again.
- A cache file that fails to parse is treated as absent, not as empty.

Caching a failure as a clean answer would be the twelfth instance of this bug, and it would be the worst one, because it would persist across runs.

### Done when

- Two consecutive scans of the same tree produce identical findings, and the second issues zero registry requests.
- A test writes a `lookupError` result through the cache layer and asserts nothing was persisted.
- A test round-trips an object with `hasInstallScripts: null` and asserts it is still `null`, not `false`, after a cache read.
- An expired entry triggers a refetch; a corrupt entry triggers a refetch.
- `--no-cache` produces byte-identical output to the pre-change behaviour.

## 3. devDependencies and peerDependencies

### The defect

`scan-lockfile.mjs:412` collects `dependencies` and `optionalDependencies`. Lines 416-421 then record devDependencies and peerDependencies in `skipped[]`.

This is honest and it is still a hole. Install scripts run for devDependencies — that is the entire INSTALL_SCRIPTS threat, and the developer machine is where the credentials are. The README calls it *"a real gap, not a scoping choice."*

aisec's own history is the demonstration: the nanoid advisory found by its self-scan arrived through vitest → vite → postcss, which is to say entirely through devDependencies.

Note the asymmetry that already exists — the *lockfile* walk covers the whole tree, so `VULN_KNOWN` and `TRUST_BOUNDARY` already see devDeps. It is only the **registry metadata rules** (DEPRECATED, PKG_UNKNOWN, PKG_NEW, PKG_LOWDL, INSTALL_SCRIPTS, NO_REPO, STALE) that stop at runtime dependencies.

### The change

Collect `devDependencies` and `peerDependencies`, and tag each collected dep with the section it came from. Default to including dev; `--no-dev` restores the old scope and records the exclusion in `skipped[]`.

Findings from a dev-only dependency carry `properties.scope: 'dev'` and say so in the message. A `postinstall` in a devDependency is a real finding, and it is also not the same finding as one in a shipped runtime dependency — the reader needs to be able to tell them apart without being told they are equivalent.

peerDependencies are collected but marked `scope: 'peer'`: they are declarations about what a consumer must supply, not necessarily anything installed here. Report them at one confidence level lower than the same finding on a direct runtime dependency.

Python: `[project.optional-dependencies]` extras are the closest analogue and are currently skipped at `scan-lockfile.mjs:439`. Collect them under `scope: 'optional'` in the same pass. `[tool.poetry.dependencies]` stays skipped — it is a separate parser, and it stays named in `skipped[]`.

### Done when

- A fixture with a `postinstall` in devDependencies produces INSTALL_SCRIPTS with `scope: 'dev'`.
- `--no-dev` reproduces the current output exactly, and adds a skip line naming what it excluded.
- The clean fixture gains no findings. (Criterion 4 of the eval is a release blocker.)
- `.aisec-baseline.json` is not regenerated. If aisec's own tree grows a finding here, it is triaged and either fixed or added with a `why`.

## 4. Config discovery breadth

### The defect

`scan-config.mjs` exports `CONFIG_NAMES` with four entries and `discoverConfigs(root)` checks exactly `join(root, name)` for each. No recursion.

Consequences:

- **Cursor** (`.cursor/mcp.json`), **Windsurf** (`mcp_config.json`), and the user-level `~/.claude.json` are invisible.
- A monorepo with `packages/*/.mcp.json` finds nothing, and the scan emits *"no agent config found"* — which is accurate about what it looked for and misleading about what exists.

The whole config layer — SECRET_INLINE, TYPOSQUAT, VERSION_UNPINNED, FS_BROAD, EXEC_SERVER, REMOTE_HTTP, REMOTE_NOAUTH, TRIFECTA — silently does not run for those users. It lands in `skipped[]`, so it is not a false clean, but it is a whole product surface that quietly never engages.

### The change

Extend `CONFIG_NAMES`:

```
.mcp.json
mcp.json
claude_desktop_config.json
.vscode/mcp.json
.cursor/mcp.json
.windsurf/mcp.json
mcp_config.json
.claude/mcp.json
```

Add a bounded recursive walk: depth ≤ 4, reusing `scan-unicode.mjs`'s `SKIP_DIR` set, capped at 50 discovered configs with the overflow recorded in `skipped[]` with the true count.

Hosts differ on schema. `parseMcpConfig` already accepts `mcpServers` or `servers`; keep that and let an unrecognised shape fail into `skipped[]` with the filename, as it does now.

**Out of scope:** reading `~/.claude.json` or any other path outside the scan root. Scanning a user's home directory because they asked to scan a project directory is a surprise, and the file frequently contains credentials. If it is wanted later it is an explicit flag, never a default.

### TRIFECTA interaction

TRIFECTA composes capabilities *across servers in one config*. With multiple configs discovered, it must not silently merge them into one imaginary agent — a Cursor config and a Claude Code config are different agents with different trust boundaries. Compute TRIFECTA **per config file**, as today. Cross-config composition is a genuinely interesting V2 rule and is not this change.

### Done when

- A fixture monorepo with two nested `.mcp.json` files produces findings from both, each attributed to its own path.
- A tree with a `.cursor/mcp.json` and no `.mcp.json` runs the config layer.
- Depth, count and skip-dir limits each have a test, and each records its overflow in `skipped[]` with the true number.
- TRIFECTA fires per-file and does not merge across files.

## 5. `aisec explain <RULE>`

### The defect

Seven reference documents carry the normative Detection and False positives text for every rule. A CLI user triaging a finding has no way to read them without finding the repository on GitHub.

`rules-sca.md` in particular exists largely to tell a reader when a finding is a false positive — PKG_UNKNOWN on a private scoped package being the headline case — and that text never reaches the person holding the finding.

### The change

```
aisec explain MCP001
aisec explain VULN_KNOWN --format text|json
aisec explain --list
```

Resolution is a static map from rule id to `references/<file>.md#<anchor>`, built at module load by parsing the reference headings. An unknown id exits 2 and prints the closest matches by Levenshtein — `lib/entropy.mjs` already exports `levenshtein`.

Print the section verbatim. No summarisation: the reference text is normative, and a paraphrase in the CLI would become a second source of truth that drifts.

### Done when

- Every id in `MODEL_ONLY_RULES` plus every deterministic rule id resolves to a section. A test enumerates all 37 and fails on any that does not — this is also a docs-drift alarm for renamed headings.
- `--list` prints all ids grouped by reference file.
- An unknown id exits 2 with suggestions.

## Rejected alternatives

**Fix the 25-dep cap by raising it without a cache.** Trades manufactured skips for registry rate-limiting, which produces `lookupError` results — and those become skips too, only now they are non-deterministic. The cache is what makes the higher cap safe.

**Make CRITICAL an alias for HIGH with a flag on the finding.** Preserves the existing scale and keeps every consumer working. Rejected: a flag that only the message text surfaces is exactly the situation today, and the point is that sorting, gating and ranking must all move. A property nobody sorts on is not a severity.

**Scan devDependencies by default with no scope tag.** Simpler, and it makes a dev-only postinstall indistinguishable from a shipped one. The project's whole thesis is that two different states must not share a representation.

**Walk the filesystem without a depth cap for configs.** An unbounded walk on an untrusted tree is a denial-of-service surface and a symlink-loop risk for a tool that is supposed to be safe to point at hostile input.

**Have `explain` summarise the reference text with the model.** The CLI has no model, and the reference text is normative. A generated summary would be a second source of truth.

---

## Sequencing

1 (CRITICAL) is independent and touches the most files — land it first, alone, so the threshold-monotonicity regression has a clean commit. 2 (cache) unblocks 3 (devDeps), which would otherwise multiply the lookup count against an uncached client. 4 (discovery) and 5 (explain) are independent of everything and can land in any order.

Each item is one commit. The eval in `tests/eval/README.md` runs before the release, not per commit — with particular attention to criterion 4, since items 3 and 4 both widen what gets scanned and false positives on the clean fixture block the release.
